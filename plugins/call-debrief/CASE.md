# Кейс: звонок → решения и задачи

Александр Петров, ГК «Диалектика». Разбор для конференции heg.ai, 12.11.2026.

## Задача

После встреч договорённости расползаются: кто что обещал, что решили, какие всплыли риски.
Это либо разбирается руками, либо теряется. У меня около 70 рабочих звонков в месяц.

Нужно было, чтобы после звонка без моего участия появлялись задачи на доске и контекст в
базе проекта. И чтобы туда не попадал мусор: лишние «задачи», чужие обещания, звонок не в
том проекте.

## Что сделали и кто пользуется

Конвейер, который разбирает каждый мой рабочий звонок. Запись падает в папку, через
несколько минут в очереди приёмки появляется черновик: решения, обещания (мои и мне),
поручения, риски, сдвиги планов, факты и предполагаемый проект с уверенностью. Я принимаю
звонок целиком, отклоняю или отправляю на переразбор с подсказкой. Только после «принять»
задачи уходят на доску, а знания в граф проекта.

Пользуюсь я сам каждый день. Принятые знания дальше читают мои агенты: трекинг клиентов,
планирование дня, подготовка текстов. Контекст они берут из графа, а не из моих пересказов.

## Как устроено

```
запись (Zoom / Телемост / диктофон)
  → наблюдатель на ноутбуке забирает файл из папки
  → транскрибация Whisper на своём сервере
  → классификатор: обещания, задачи, проект      (prompts/classifier.md)
  → извлечение знаний: решения, риски, факты     (prompts/knowledge.md)
  → очередь приёмки: принять / отклонить / переразобрать с подсказкой
  → после «принять»: задачи на доску, знания в граф проекта (Мионика)
```

- **Модель:** Claude Sonnet 4.6, структурный выход через принудительный вызов инструмента
  со схемой (`schema/debrief.schema.json`). Модель не может пропустить поле или придумать
  своё.
- **Проекты:** классификатор получает живой список проектов из графа. Ключ проекта он берёт
  только из этого списка. Если уверенность ниже 0,7, контекст не пишется, а человеку
  уходит вопрос «куда положить».
- **Знания отдельно от проекта:** второй проход не знает проекта. Если при приёмке проект
  меняют, повторно разбирать транскрипт не нужно.
- **Инфраструктура:** один VPS (транскрибация, классификатор, сервис приёмки), сервис на
  Python, SQLite для состояния.

В репозитории три части. Скил `call-debrief` — разбор и приёмка в чате: ставится одной командой и
работает без сервера. Сервис [`services/call-pipeline`](../../services/call-pipeline) — транскрибация,
диаризация, запись Телемоста и веб-кабинет. Сервис [`services/ops-ingest`](../../services/ops-ingest) —
очередь приёмки и запись принятого в Мионику, а без неё в файлы.

## Путь и эффект

**Июнь.** Первая версия: транскрибация и разбор, задачи переносил руками.

**Июль–август.** Дали агенту писать в базу знаний самому, с порогом уверенности по проекту.
Стало видно, что ошибки маршрутизации и лишние «задачи» приходится вычищать задним числом, и
это дороже, чем проверять до записи.

**Сентябрь.** Вернули приёмку, но не поатомную: на звонок выходит около 25 пунктов, и
галочки на таком объёме начинают жать не глядя. Единица проверки стала одна: звонок
целиком, три действия.

**Цифры на 18.10.2026** (из базы сервиса, не оценки):

| | |
|---|---|
| Звонков через конвейер с 19.06 | 337, около 256 часов записей |
| Решений в очереди с 06.09 | 143: принято 79, отклонено 64 |
| Принято с первого раза | 59% |
| Принято после смены проекта | 30% (сами пункты не правились) |
| Принято после переразбора с подсказкой | 10% (в основном имена и кто что сказал) |
| Пунктов с принятого звонка | медиана 26: 14 знаний и 12 задач |
| Активное время на решение по звонку | около минуты, 3–6 минут в день |

Сколько времени уходило на ручной разбор до конвейера, никто не замерял. Стоимость прогона
на звонок пока не логируется. Поэтому эти цифры я не называю.

## Где применимо и как адаптировать

**Подходит**, если у вас много встреч и договорённости из них должны куда-то попадать:
руководитель проектов, консультант, продажи, трекер, фаундер. Начать можно со скила в
этом репо, без сервера: дайте расшифровку из любого сервиса и примите разбор в чате.

**Что нужно для запуска:** Claude Code и 15 минут (см. `README.md`), свой список проектов в
`context/projects.md`, своё имя в `context/me.md`. Для своего конвейера дополнительно: сервер
под [`services/call-pipeline`](../../services/call-pipeline) и
[`services/ops-ingest`](../../services/ops-ingest).

**Ограничения:**
- Без разметки говорящих атрибуция «кто что обещал» заметно хуже.
- Чужие записи (вебинары, присланные звонки) надо отсекать: модель должна сказать, что
  владельца в записи нет, а не приписывать ему чужие обещания.
- Данные звонка уходят в модель. Персональные и чужие конфиденциальные данные сначала
  обезличить.
- Промпт учится на отказах. Записывайте причину отклонения и счётчик переразборов, иначе
  непонятно, что чинить.

**Три вещи, которые я бы сделал сразу:**
1. Приёмку до записи в базу, а не чистку после.
2. Проверку звонка целиком, а не поатомные галочки.
3. Неуверенность в выходе модели: опознан ли владелец, между какими проектами она
   колебалась. Низкая уверенность означает вопрос человеку, а не догадку.
